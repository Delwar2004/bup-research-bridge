## 1. API overview

BUP Research Bridge is a web platform for the CSE and ICT departments of Bangladesh University of Professionals. The API lets four account roles share one research directory:

- Students discover faculty, alumni, thesis and research opportunities, and previous research work, then request mentorship.
- Faculty manage a research profile, publications, and thesis or research opportunities, and respond to mentorship.
- Alumni manage a professional profile, experiences, publications, previous research records, and mentorship.
- Administrators activate accounts, manage role records, moderate content, read activity logs, and read activity reports.

The API is JSON over HTTP, versioned, and backed only by PostgreSQL. Search uses the existing `tsvector` and `pg_trgm` indexes. There is no Elasticsearch, file-storage service, or separate application table.

## 3. Authentication strategy

The database already defines the mechanism. This contract does not add a second one.

| Piece | Where it lives | Rule |
| --- | --- | --- |
| Password | `users.password_hash` | One-way Argon2id or bcrypt. Never reversible encryption, never returned. |
| Access token | Not stored | JWT. Short-lived. Stateless. |
| Refresh token | `refresh_tokens.token_hash` | Random secret, stored only as a hash of length 32–128. Raw token is returned once, to the client. |
| Logout | `refresh_tokens.revoked_at` | Set on logout. FR-04. |
| Last login | `users.last_login_at` | Set on successful login. Must be `>= created_at`. |

### 3.1 Token rules

- Access token lifetime: 15 minutes.
- Refresh token lifetime: 14 days, and `expires_at > created_at`.
- Access token claims: `sub` (user id), `role`, `status`, `iat`, `exp`. No email, no profile fields, no password material.
- Signing algorithm: HS256 or RS256. The key is server configuration, not a database column.
- Refresh rotates on every successful `POST /auth/refresh`: the presented token is revoked and a new row is inserted in the same transaction.
- A refresh token is rejected when it is unknown, expired, revoked, or the account is not `active`.
- Logout does not delete the row. It sets `revoked_at`.
- Access tokens cannot be revoked individually. They expire. Logout-all revokes every refresh token for that user.

### 3.2 Account status and login

`users.status` defaults to `pending`.

| Status | Self-registration | Login and refresh |
| --- | --- | --- |
| `pending` | Result of public registration | Rejected after the password matches |
| `active` | Only when an administrator creates the account and sets this status | Allowed |
| `suspended` | Not a registration result | Rejected after the password matches |
| `rejected` | Not a registration result | Rejected after the password matches |

Wrong email or wrong password is always `401`, including for inactive accounts, so status is not revealed to someone who does not know the password.

Triggers call `fn_assert_active_roles` for new opportunities, projects, publications, and mentorship requests. The API therefore requires `status = active` on every protected route, not only at login.

### 3.3 Who may register

| Caller | Roles they may create |
| --- | --- |
| Public `POST /auth/register` | `student`, `faculty`, `alumni` |
| Administrator `POST /admin/users` | `student`, `faculty`, `alumni`, `admin` |

An administrator account has no row in `students`, `faculty`, or `alumni`. The first administrator is created operationally (a one-off insert or a bootstrap command), not by public registration. That bootstrap is outside this contract. See gap G-04.

### 3.4 Password rules (application)

The database checks the **hash** length (20–512), not the plaintext. Before hashing, the API requires:

- Type string.
- Length 8 through 72 characters (72 keeps bcrypt from silently truncating; Argon2id is also acceptable).
- No leading or trailing whitespace requirement beyond the raw string the user typed. The value is not trimmed, so a space inside the password is significant.

The plaintext password is never logged, never stored, and never placed in `activity_logs.metadata` or notification `payload`.

## 4. Authorization and RBAC

`users.role` is the current authorization role: `student`, `faculty`, `alumni`, `admin`.

Historical profile rows may remain after a role change. Directory reads use the active role only, matching view `v_user_profiles`. A person who was faculty and is now alumni still owns old `thesis_opportunities` rows, because `faculty_user_id` points at the retained `faculty` row.

### 4.1 Role matrix

| Capability | Student | Faculty | Alumni | Admin |
| --- | --- | --- | --- | --- |
| Register self | Yes | Yes | Yes | No |
| Read own account | Yes | Yes | Yes | Yes |
| Update own profile | Yes | Yes | Yes | Name and email only |
| Browse active faculty and alumni | Yes | Yes | Yes | Yes |
| Browse other students | No | No | No | Yes |
| Create opportunity | No | Yes, as owner | No | Yes, for an active faculty owner |
| Update own opportunity text | No | Owner | No | Any |
| Change opportunity availability | No | Owner, while role is still `faculty` | No | Any |
| Submit content for review | No | Own | Own publications and projects | Not required |
| Moderate content | No | No | No | Yes |
| Create publication or repository project | No | Yes | Yes | Yes |
| Be an author or project member | Yes, if a student profile row exists | Yes | Yes | No. Admin-only accounts fail `fn_assert_academic_profile` |
| Create mentorship request | Yes | No | No | No |
| Accept, reject, or complete a request | No | If they are the mentor | If they are the mentor | No |
| Cancel a request | If they are the student | No | No | No |
| Post a message on a request | If they are the student | If they are the mentor | If they are the mentor | No |
| Read message bodies | Party to that request | Party to that request | Party to that request | No |
| Read own notifications | Yes | Yes | Yes | Yes |
| Manage accounts, logs, reports | No | No | No | Yes |

Department authority is a proposal stakeholder with no `user_role` value and no table. This API has no department-authority endpoints. See gap G-05.

### 4.2 Content visibility

`moderation_status`: `draft`, `pending`, `approved`, `rejected`, `archived`.

`availability_status` (opportunities only): `open`, `closed`, `filled`.

| Reader | Opportunities, projects, publications |
| --- | --- |
| Student, faculty, alumni who do not own the row | `moderation_status = approved` only. Opportunities also default to `availability_status = open` unless a filter says otherwise. |
| Owner (`faculty_user_id` or `created_by_user_id` matching the caller) | All of their moderation states, including draft. |
| Administrator | All rows. |

Email is omitted from directory and public profile responses. Email is returned to the account owner and to administrators. `password_hash`, `token_hash`, `client_ip`, and `user_agent` are never returned.

An inactive user (`pending`, `suspended`, `rejected`) is omitted from faculty and alumni directories. Administrators can still load them through `/admin/users`.

### 4.3 Protected and public endpoints

Public (no access token):

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/refresh`
- `POST /auth/logout`
- `GET /departments`
- `GET /research-areas` (a bearer token is optional and is used only to reveal inactive areas to an administrator)

Every other endpoint requires `Authorization: Bearer {accessToken}` and an `active` account.

`POST /auth/logout` accepts a refresh token in the body and does not require an access token, so a client can sign out after the access token has expired.

## 6. Common response format

Success:

```json
{
  "success": true,
  "message": "Human-readable summary.",
  "data": {},
  "meta": {}
}
```

- `data` is an object, an array, or `null`.
- `meta` is present on paginated lists and on search. It is omitted on single-resource responses.
- `message` is a short sentence, not a translation key.

This envelope is used for every status, including creates and deletes. `204 No Content` is not used.

Error:

```json
{
  "success": false,
  "message": "Human-readable summary.",
  "error": {
    "code": "VALIDATION_ERROR",
    "details": {
      "fields": [
        {
          "field": "email",
          "rule": "format",
          "message": "Email must look like a mailbox address."
        }
      ]
    }
  }
}
```

`details` may be `{}` when there is no field list. `details.fields` is present for `422`.

## 7. Common error format

| HTTP | `error.code` | When |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | Malformed JSON, wrong type at the JSON-syntax level, or a query parameter that cannot be parsed (not a UUID, not an integer). |
| 401 | `UNAUTHORIZED` | Missing or invalid access token, or invalid credentials at login. |
| 403 | `FORBIDDEN` | Authenticated, but the role, ownership, or account status does not allow the action. |
| 403 | `ACCOUNT_PENDING` | Password matched and status is `pending`. |
| 403 | `ACCOUNT_SUSPENDED` | Password matched and status is `suspended`. |
| 403 | `ACCOUNT_REJECTED` | Password matched and status is `rejected`. |
| 404 | `NOT_FOUND` | The resource does not exist, or it exists but this caller must not learn that it exists. Hidden content uses `404`, not `403`. |
| 406 | `NOT_ACCEPTABLE` | `Accept` does not allow JSON. |
| 409 | `CONFLICT` | Unique violation: email, department code or name, research-area slug or name, publication DOI, duplicate pending mentorship request. |
| 422 | `VALIDATION_ERROR` | A check constraint, foreign key, enum, or documented business rule failed. |
| 500 | `INTERNAL_ERROR` | Unexpected failure. No SQL text and no stack trace in the body. |

`401` body:

```json
{
  "success": false,
  "message": "Authentication is required.",
  "error": { "code": "UNAUTHORIZED", "details": {} }
}
```

`403` body when the role is wrong:

```json
{
  "success": false,
  "message": "You cannot perform this action.",
  "error": { "code": "FORBIDDEN", "details": {} }
}
```

Every protected endpoint may return `401`, `403` (`FORBIDDEN` or an account-status code if a token for a non-active user is ever presented), and `500`. Those three are not repeated on every endpoint below. Endpoints list the additional errors that are meaningful for that operation.

## 8. Pagination, filtering, and search conventions

### 8.1 Pagination

Page strategy, not cursors.

| Query | Type | Default | Rules |
| --- | --- | --- | --- |
| `page` | integer | `1` | Minimum 1. |
| `pageSize` | integer | `20` | Minimum 1. Maximum 100. |

`meta` on list and search responses:

```json
{
  "page": 1,
  "pageSize": 20,
  "totalItems": 0,
  "totalPages": 0
}
```

`totalPages` is `0` when `totalItems` is `0`. Otherwise it is `ceil(totalItems / pageSize)`.

A `page` past the end returns `200` with `data: []` and the real `totalItems`. It is not a `404`.

Single-resource reads, `GET /departments`, `GET /research-areas`, `GET /auth/me`, and `GET /notifications/unread-count` are not paginated.

Message threads use the same page parameters with default `pageSize` 50 and maximum 100, ordered by `created_at` ascending.

### 8.2 Sorting

| Query | Type | Default |
| --- | --- | --- |
| `sort` | string allow-list per endpoint | Documented on that endpoint |
| `order` | `asc` or `desc` | `desc` when `sort` is a timestamp, otherwise the endpoint default |

Any other `sort` or `order` value is `400`.

### 8.3 Repeated filters

`researchAreaId` may be repeated. `researchAreaMatch` is `any` (default) or `all`.

- `any`: the row is linked to at least one of the given areas.
- `all`: the row is linked to every given area.

Each value must be a UUID. Unknown ids produce `422`, not an empty silent filter.

### 8.4 Keyword search

`q` is an optional string on list endpoints and a required string on `GET /search`.

- Trimmed length 1–200 after trim. Empty after trim is treated as omitted on list endpoints and `422` on `GET /search`.
- Opportunities, projects, and publications: `search_vector @@ websearch_to_tsquery('english', q)` using the generated column already on those tables.
- Faculty and alumni names: `pg_trgm` on `users.full_name` (`ILIKE` with the trigram index). Email is not a public search field.
- No separate search engine.

List filters combine with `AND`. Text search and research-area filters combine with `AND`.

Success `201`:

```json
{
  "success": true,
  "message": "Account created and is waiting for an administrator to activate it.",
  "data": {
    "id": "uuid",
    "fullName": "string",
    "email": "string",
    "role": "student",
```

No tokens are issued. `status` is always `pending`.

Errors: `409 CONFLICT` duplicate email. `422` unknown department, inactive or unknown research area, missing role field, or `role = admin`.

Transaction: insert `users` and the matching profile, then junction rows, before commit. The deferred profile trigger rejects a non-admin user with no profile.

#### AUTH-02 Login

| | |
| --- | --- |
| Method | `POST` |
| Path | `/auth/login` |
| Purpose | Verify the password and issue an access token plus a refresh token. |
| Authentication | No |
| Roles | Any active account |
| Database | `users`, `refresh_tokens` |
| Requirements | FR-02, FR-04, FR-32 |

Body:

| Field | Type | Required | Validation |
| --- | --- | --- | --- |
| `email` | string | Yes | Mailbox shape |
| `password` | string | Yes | 1–72 characters. Compared with the hash only. |

Success `200` `data`:

| Field | Type | Meaning |
| --- | --- | --- |
| `accessToken` | string | JWT |
| `accessTokenExpiresAt` | date-time | |
| `refreshToken` | string | Raw secret. Shown once. |
| `refreshTokenExpiresAt` | date-time | |
| `user` | private account plus active profile fields from §9.3 and §9.4 | Password fields absent |

Side effect: set `users.last_login_at = now()` and insert `refresh_tokens` (hash, `expires_at`, optional `user_agent` from the `User-Agent` header truncated to 500 characters, optional `client_ip`). Those two writes are one transaction. `user_agent` and `client_ip` are not returned.

Errors:

| HTTP | Code | When |
| --- | --- | --- |
| 401 | `UNAUTHORIZED` | Unknown email or password mismatch. Message: `Invalid email or password.` |
| 403 | `ACCOUNT_PENDING` | Password matched, status `pending` |
| 403 | `ACCOUNT_SUSPENDED` | Password matched, status `suspended` |
| 403 | `ACCOUNT_REJECTED` | Password matched, status `rejected` |

#### AUTH-03 Refresh

| | |
| --- | --- |
| Method | `POST` |
| Path | `/auth/refresh` |
| Purpose | Exchange a live refresh token for a new pair and revoke the presented token. |
| Authentication | No |
| Database | `refresh_tokens`, `users` |
| Requirements | FR-02, FR-04 |

Body: `{ "refreshToken": "string" }` required.

Success `200`: same token payload shape as login, without repeating the full profile. `data.user` is `{ id, role, status }`.

Errors: `401` when the token is missing, unknown, expired, revoked, or the hash does not match. `403` account-status codes when the account is no longer `active`.

Transaction: revoke the old row (`revoked_at = now()`) and insert the new row together. Reuse of a revoked token does not issue a new token.

#### AUTH-04 Logout

| | |
| --- | --- |
| Method | `POST` |
| Path | `/auth/logout` |
| Purpose | Revoke the presented refresh token. |
| Authentication | No |
| Database | `refresh_tokens` |
| Requirements | FR-04 |

Body: `{ "refreshToken": "string" }` required.

Success `200`: `data` is null and `message` is `Logged out.` The same response is returned when the token is unknown, already revoked, or expired, so the endpoint does not confirm that a token existed.

Success `200`: `data.revokedCount` is the number of rows updated.

#### AUTH-07 Change password

| | |
| --- | --- |
| Method | `POST` |
| Path | `/auth/password` |
| Purpose | Replace the caller's password hash. |
| Authentication | Yes |
| Roles | Any active role |

Body:

| Field | Type | Required | Validation |

### 12.9 Mentorship

Workflow supported by `mentorship_requests` and the proposal sequence:

1. Student finds a faculty member or alumnus (PROF-03, PROF-05, SRCH-01) and optionally an opening (OPP-02).
2. Student creates a request (MEN-01). The database requires the student to be an active `student` and the mentor to be an active `faculty` or `alumni`.
3. The mentor is notified (`mentorship_requested`).
4. Mentor accepts or rejects, or the student cancels (MEN-04).
5. The other party is notified (`mentorship_updated`).
6. Either party posts messages (MEN-06). The other party is notified (`message_received`).

#### Status transitions

The database enum does not encode a graph. The API accepts only these transitions so a request cannot be reopened by a stray value:

| From | To | Who |
| --- | --- | --- |
| `pending` | `accepted` | Mentor |
| `pending` | `rejected` | Mentor |
| `pending` | `cancelled` | Student |
| `accepted` | `completed` | Mentor |
| `accepted` | `cancelled` | Student |

`rejected`, `cancelled`, and `completed` are terminal. Any other jump is `409`.

Leaving `pending` stamps `responded_at` in the database when it is still null.

#### MEN-01 Create mentorship request

| | |
| --- | --- |
| Method | `POST` |
| Path | `/mentorship-requests` |
| Purpose | Student asks a faculty member or alumnus for mentorship, with or without an opening. |
| Authentication | Yes |
| Roles | `student` |
| Database | `mentorship_requests`, `mentorship_messages`, `notifications` |
| Requirements | FR-29, FR-30, and the mentorship sequence |

Body:

| Field | Type | Required | Validation |
| --- | --- | --- | --- |
| `mentorUserId` | uuid | Yes | Active `faculty` or `alumni`. Not the student. |
| `opportunityId` | uuid | No | If sent, the opportunity must exist, be `approved`, and be `open`. |
| `subject` | string | Yes | Trimmed 1–200 |
| `message` | string | Yes | Trimmed 1–10000. Stored as the first message, not on the request row. |

| HTTP | When |
| --- | --- |
| 403 | Caller is not an active student |

| 409 | A `pending` request already exists for this student and mentor with the same `opportunityId`, or for this pair with both opportunity ids null. Index names: `mentorship_requests_one_pending_opportunity_idx`, `mentorship_requests_one_pending_general_idx`. |
| 422 | Mentor is the student, or the mentor's current role is not faculty or alumni |

1. Insert `mentorship_requests` with status `pending`.
2. Insert `mentorship_messages` with `sender_user_id` = student and `body` = `message`.
3. Insert `notifications` for the mentor: type `mentorship_requested`, `mentorship_request_id` set, `message` a short sentence that includes the subject, `payload` `{ "requestId", "subject" }`.

A second pending request is allowed when the opportunity differs, or when an earlier request is no longer `pending`.

After a student account becomes alumni, the old `students` row remains and old requests remain readable. New requests fail because the current role is no longer `student`.

When ADM-07 sets an opportunity to `approved`, the API inserts one `opportunity_published` notification for every user with `role = student` and `status = active`.

`message` example: `A new research opportunity was published: {title}.` Length must stay within 2000 characters; truncate the title if needed.

`opportunity_id` is set. `payload` is `{ "opportunityId", "title" }`.

The proposal says "users" and does not name the audience. This contract notifies active students, because they are who FR-12 addresses. Faculty and alumni are not fan-out recipients. See gap G-06.

The owner receives a separate `content_moderated` notification, not a second `opportunity_published` row, when an administrator approves, rejects, or archives their content.

## 16. Transaction considerations

Implement these as single database transactions. Do not implement them in this phase.

| Operation | Writes that commit or roll back together |
| --- | --- |
| AUTH-01 register | `users`, role profile, optional research-area links. Deferred profile trigger runs at commit. |
| AUTH-02 login | `last_login_at` and `refresh_tokens` insert. |
| AUTH-03 refresh | Revoke presented token and insert the replacement. |
| AUTH-07 password | Update `password_hash` and revoke every refresh token. |
| PROF-02 | Replace one role's junction rows. |
| OPP-01, PRJ-01, PUB-01 | Parent row plus areas and, where relevant, members or authors. |
| OPP-04, PRJ-04, PUB-04 | Parent update and, when the array is present, full replacement of children. If the parent is approved, the deferred "at least one" triggers run at commit. |
| OPP-07 delete | Delete parent. Fails the transaction if a mentorship request still references it. |
| MEN-01 | Request, first message, mentor notification. |
| MEN-04 | Status update (database stamps `responded_at`) and notification to the other party. |
| MEN-06 | Message and `message_received` notification. |
| ADM-02 | User, profile, links, activity log, and conditional account notification. |
| ADM-04 | User update, token revocation when status is not active, notification, activity log. |
| ADM-05 | `users.role`, insert missing profile, notification, activity log. Order is role update then profile insert. |
| ADM-07 approve | Moderation update (`published_at` stamp), owner notification, one notification per active student, activity log. |
| ADM-07 reject or archive, ADM-08, ADM-09 | Moderation update, owner notification, activity log. |
| Administrator content edit or delete | The content change and one `activity_logs` row. |

Activity-log `action` values written by this contract:

## 18. Known gaps and ambiguities

These are reported. They are not fixed in the database and they are not papered over with new columns.

| ID | Topic | What the sources say | Contract decision |
| --- | --- | --- | --- |
| G-01 | NFR-04 wording | NFR-04 says "encryption". `users.password_hash` comments require Argon2id or bcrypt. | API hashes passwords. It does not store reversible ciphertext. |
| G-02 | Figure 1 | The PDF ER diagram is not the migration schema. Polymorphic author and mentorship keys were not implemented. | API follows migrations `001`–`007`. |
| G-03 | Role change | Triggers allow a student to become alumni only when an alumni profile exists, and they keep the student row. No FR names graduation. | ADM-05 exists so FR-24 can change a role without breaking the trigger. It is schema support, not a new product feature. |
| G-04 | First administrator | FR-01 includes administrators. Public registration of `admin` would be unsafe, and no seed user exists. | Public register rejects `admin`. An operator creates the first admin outside this API. |
| G-05 | Department authority | Stakeholder in §5. No role enum and no table. | No endpoints. |
| G-06 | FR-27 audience | "Notify users" does not say which users. | Fan-out to active students when an opportunity is approved. |
| G-07 | Research-area administration | Filters need the vocabulary. The proposal does not list a screen for it. Seed data ships 13 areas. | ADM-12 and ADM-13 create and deactivate. No delete, because references use `ON DELETE RESTRICT`. |
| G-08 | Student research interests | `student_research_areas` exists. No FR says students declare interests. | PROF-02 allows it under FR-26. It is not a matching or recommendation engine. |
| G-09 | Slots versus accepted requests | `slots` is an integer. Nothing counts accepted mentorships. | Faculty set `filled` manually. The API does not invent a counter. |
| G-10 | Last administrator | An admin can suspend themselves. No guard column exists. | Allowed. Operations must keep another active admin. |
| G-11 | "Upload" publications | FR-07 says upload. The table has metadata and a URL, not a file bytea or object-storage key. | JSON metadata and an optional URL. No multipart file endpoint. |
| G-12 | Deleting users | Many foreign keys are `ON DELETE RESTRICT` (`created_by`, mentorship, authors). | No user-delete endpoint. `suspended` and `rejected` are the account actions. |
| G-13 | External academic systems | NFR-14. Proposal §4.4 excludes journal and conference integration. | No integration endpoints in v1. |
| G-14 | Registration approval | Schema default status is `pending`. The proposal does not say an admin must approve signups. | The API follows the schema. Pending users cannot log in until ADM-04 sets `active`. |
| G-15 | Opportunity applications | No application table. | Not built. Mentorship plus optional `opportunityId` is the only student action on an opening. |

## 19. Out of scope

The following are not in this contract, because proposal §4.4 or the schema excludes them:

- Research paper submission and review workflow.
- Conference management.
- External journal submission.
- Video or voice calls.
- Payments.
- Mobile-application APIs. The web API is what browser clients, including mobile browsers, will call.
- Job board or recruitment.
- Elasticsearch or another search engine.
- Group chat and direct messages outside mentorship.
- Citation graphs, peer review, and acceptance workflows.
- Binary file upload.
- Notification preference management.
- A public unauthenticated directory. FR-32 plus FR-02 keep research content behind authentication. Department and research-area lists are public only because registration needs them.

## 20. Security considerations

- Passwords and refresh-token secrets appear only in the login and refresh success bodies (the refresh secret) and in the password-change request. They are never echoed back on later reads.
- Compare passwords with a hash verifier. Do not compare plaintext to a decrypted value.
- Use parameterized SQL only.
- Treat UUID path parameters that fail to parse as `400`, not as a database cast error page.
- Return `404` for drafts and for profiles the caller must not see, so existence is not a signal.
- Do not put message bodies, password hashes, or tokens into `activity_logs.metadata` or server error responses.
- `refresh_tokens.client_ip` and `user_agent` are written for operational tracing and are not part of any response in this contract.
- CORS is a deployment concern. Browsers are the intended client (NFR-10, NFR-11). No additional public origin is granted by this document.
- Administrator report and log endpoints are the sensitive reads. They require `role = admin`.
